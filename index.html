SetBook — Technical Documentation

Last updated 2026-09-23.

1. Overview 2. Architecture 3. Data model 4. Song library 5. Section editor 6. Live preview 7. PDF export 8. File management 9. Device transfer 10. Requirements 11. Maintainer notes 12. QA regression checklist

1. Overview

SetBook is a single-file, client-side web application for building and managing a personal song library as structured lead sheets. It is designed for musicians who need readable chord charts at rehearsals, jam sessions, open mics, recording sessions, and live performances.

The entire application — markup, styles, and logic — is contained in one HTML file. There is no build step, no backend, no account system, and no local database. Third-party code is loaded from CDNs at runtime: jsPDF (PDF generation) and Google Fonts (typefaces). All UI icons are inline SVG assets embedded directly in the file, so they render with no network access.

2. Architecture

  • All application state is held in a single in-memory state object. Rendering is performed by a set of render functions (renderSidebar, renderMain, renderPreview) that rebuild their panes from that state.
  • PDF generation is handled by the jsPDF library with a custom embedded monospace typeface (IBM Plex Mono, regular and bold), fetched once per session from a CDN and cached in memory, with graceful fallback if the fetch fails.
  • Appearance is controlled by a data-theme attribute on the <html> element. The default theme is dark; a light theme follows the device's system preference. The choice can be overridden in File → Configuration…, and is persisted on the device.
  • Layout consists of a resizable song-library sidebar alongside the main editor column, and adapts responsively down to phone widths.

3. Data model

All persistent data is a JSON serialization of the state object:

  • sectionGroups[] — songs. Fields: id, name (title), artist, videoUrl (optional reference link), type ("cover" | "original", defaults to "cover"), readyStatus ("ready" | "not-ready", defaults to "not-ready").
  • sections[] — song sections. Fields: id, groupId (owning song), nameType (one of "intro", "verse", "chorus", "pre-chorus", "bridge", "instrumental", "outro", or "custom"), customName (free text, used when nameType is "custom"), nameSuffix (optional informational tag appended after the number, e.g. "(guitar solo)"), order (position within the song), lines[], and name — the derived display name, stamped at save time so the raw JSON stays readable and older SetBook versions still show a sensible title. The visible name is computed by displaySectionName(): sections sharing a base name within a song are numbered ("Chorus" alone, but "Chorus 1" / "Chorus 2" when there are two); custom names take part in the counting too, and a user-typed trailing number (e.g. a legacy custom "Verse 1") is ignored for grouping so numbering is never doubled. The Number single sections setting (File → Configuration…) also numbers sections that appear only once ("Chorus 1" instead of "Chorus"); it is stored per file as numberSingleSections and defaults to off. Files saved before the name picker existed only have name; on load the whole old title becomes a custom name, with a trailing parenthetical aside moved into nameSuffix.
  • Line — { text, symbols[] }. text is the lyric line; symbols is an array of { pos, value } placing each chord symbol at an absolute character offset within the row, so chords stay aligned over the correct lyric characters in the preview and in PDF output.
  • songSubsets[] — named song selections, { id, name, songIds[] }, used to scope which songs are included in a PDF export.
  • UI preferences persisted in the file: projectName, songSort { field, dir }, sidebarWidth, songTypeFilter, readyFilter, numberSingleSections, focusedGroupId, lastFolderName.

4. Song library (sidebar)

  • Songs are listed alphabetically with their sections nested beneath. Songs can be expanded and collapsed individually or all at once.
  • Search is a case-insensitive substring match across song title, artist, section name, lyric text, and chord symbols. Matches are shown per section with a snippet of the matching lyric line. The Cover/Original and Ready/Not ready filters apply to search results as well as to browsing.
  • Sorting is by title or artist, ascending or descending. Untitled songs are pinned below titled songs in both directions; songs without an artist are pinned below songs that have one. A leading "The " in an artist name is ignored for ordering ("The Beatles" sorts under B).
  • Filter toggles: Cover/Original and Ready/Not ready. Each song carries a clickable status badge that flips its value. If a filter hides the song currently open in the editor, the editor closes back to the empty starting view; restoring the filter does not reopen anything.
  • Focus mode: the ◎ button on a song header hides the search box, sort/filter/expand controls, the "+ New song" button, and all other songs, leaving just that song with its sections — always expanded and still fully editable (select, reorder, add, and delete sections all work). Entering focus also opens the focused song's top section in the editor, so no section from a previously viewed song lingers under the new song's name. The "← All songs" bar at the top exits focus. The choice is saved per file and survives reload; deleting the focused song exits focus automatically.
  • Per-song metadata: editable title and artist, optional video link (with open/edit controls), Cover/Original badge, and Ready/Not Ready badge.
  • Configuration: the File menu's Configuration… item opens a preferences modal. Appearance (dark/light) and Watch video links (new tab / same tab) are saved per device; Number single sections is saved in the file.

5. Section editor

  • Each section is an ordered list of rows. Every row has a chord-entry field and a lyric-text field. New songs start with an empty "Intro" section.
  • Keyboard navigation: ArrowUp/ArrowDown move vertically between fields; pressing Down in the last lyric field appends a new row.
  • Chord entry is tokenized on whitespace; each token becomes a chord symbol positioned at its character offset, keeping chords aligned over the lyric line.
  • Bulk paste: pasting multiple lines into the editor alternates chord/lyric pairing automatically.
  • Sections can be added, moved up and down, and deleted; renaming is done through the name picker in the editor header.
  • Section names are chosen from a picker: Intro, Verse, Chorus, Pre-Chorus, Bridge, Instrumental, Outro, or Custom (free text). A tag field next to the picker holds informational text shown after the number, e.g. (guitar solo); a "Shows as" line under the picker previews the final derived name.
  • Numbering is automatic and always derived from the current sections: a lone Chorus is shown as Chorus, but two Choruses in one song become Chorus 1 and Chorus 2 — deleting or retyping one renumbers the rest. Custom names are counted as well, so a custom Chorus numbers together with a picked Chorus. The Number single sections setting (File → Configuration…) numbers lone sections too (Chorus 1); it is saved per file and defaults to off. The derived name is used everywhere: sidebar, preview, search, and both PDF pipelines.
  • "+ Add section" picks its type from the bottom section's name: after a Verse comes a Chorus; after a Chorus, Bridge, or Instrumental comes a Verse; a Pre-Chorus leads into a Chorus; anything else (Intro, Outro, Custom, untitled) starts a Verse. Matching is by name prefix, so "Chorus 2" and a custom "Chorus (reprise)" count as choruses. "Create copy of section" copies the section's type along with its lyrics.
  • Row actions: each row has Clear chords and Clear lyrics buttons above its fields (these clear one input only), plus icon buttons at the right edge to move the row up, move it down, copy it (duplicate icon), and delete it. Copying duplicates the row's chords and lyrics and appends the copy at the bottom of the section, then scrolls it into view.
  • Comment lines: a lyric line wrapped in /* … */ is a private note. It remains visible in the editor and the preview but is excluded from PDF exports.
  • Lyric continuation rows: a lyric-only row that follows a row containing both chords and lyrics is rendered stacked beneath that row's lyric line, under the same chord line, in the preview and in PDFs. The editor keeps one row per source line.
  • Repeat shorthand: if a row's chord line contains a standalone (xN) token and its lyric line contains the same (xN), the row is understood to repeat N times. The preview and both PDF pipelines strip both tokens and display a single condensed (xN) marker one character to the right of the widest line, vertically centered between the chord and lyric lines. Editor source data is never modified by this transform.

6. Live preview

The preview pane renders the currently selected section through the same display-block grouping logic (groupLinesForDisplay) used by the PDF pipelines, so what is shown on screen matches the exported layout, minus PDF pagination.

7. PDF export

  • Performance PDF. One page per song section (long sections paginate across pages). The page is sized for a target device — picked from a grouped dropdown of iPad models (10.2", 10.9"/11", Pro 11", Pro 12.9"/13", mini 7.9", mini 8.3"), iPhones (SE, 14/15/16, Pro Max), Android tablets and phones by screen size, or US Letter/A4 paper — in portrait or landscape, rendered in dark or light mode. It includes a tappable table of contents, one title page per song, a "back to Contents" link and the song title on every page, and previous/next-section navigation links at the bottom of each section page. The body font size is unified per song — every section page within one song uses the same size, the largest at which all of that song's sections still fit on their pages (the minimum of the per-section best-fit sizes, picked from fixed tiers so content fits without overflow); the layout is designed for use with Bluetooth page-turner pedals.
  • Print-Friendly PDF. A continuous document stacking all selected songs and sections with page numbers. The body font size is auto-selected once for the whole document.
  • Both pipelines use the embedded IBM Plex Mono typeface so chord alignment is exact in any PDF viewer.
  • Export scope: all songs in the library, one saved subset, or a manual per-song checklist. The checklist offers bulk selection — Select all, Select none, and Ready only (songs whose ready status is Ready). Like a manual checkbox change, a bulk selection clears the subset dropdown so the selection is clearly custom.

8. File management

  • Libraries are stored as .json files. In browsers that support the File System Access API (Chrome, Edge), SetBook opens a file by handle and autosaves back to it as you work; a default folder can be linked for quicker access. Other browsers (Safari, Firefox) fall back to explicit open and save-as download flows.
  • Import: songs can be copied from another SetBook JSON file via the File menu. Each song's type and ready status are carried over, defaulting to Cover / Not Ready when the source file does not specify them. Section names are carried over too — titles from files saved before the name picker become Custom names (with any trailing parenthetical moved into the tag slot).

9. Device transfer

The share button in the header opens step-by-step guides for transferring exported PDFs to reading devices. Current guides: Apple Books on iPhone/iPad, and Files by Google on Android. The guide set is extensible — additional destinations can be added to the built-in hub.

10. Requirements

A modern browser with JavaScript enabled. Internet access is required on first load to fetch the jsPDF library and fonts from CDNs; afterwards the application runs entirely from the single local file.

11. Maintainer notes

  • All display-affecting transforms (lyric-continuation grouping, comment-line stripping, repeat markers) are centralized in groupLinesForDisplay and its helpers so the preview and both PDF pipelines share one code path. Editor source data is never mutated by display logic.
  • UI icons are hand-drawn inline SVGs (<svg class="svg-icon" viewBox="0 0 512 512">) embedded directly in the markup — there is no icon font or icon CDN. To add an icon, inline a new SVG with the svg-icon class; it sizes to 1em and inherits currentColor. Do not reintroduce an external icon library.
  • Section display names are derived in exactly one place — displaySectionName(), with sectionBaseName() and migrateSectionName() beside it. Never read sec.name for display; sec.name is only stamped at save time by stampSectionDisplayNames() for JSON readability and backwards compatibility.
  • Sidebar focus state lives in state.focusedGroupId (null = off). Enter and exit focus only through setSongFocus() so search-clearing, persistence, and re-rendering stay together; renderSidebar() reads the flag to hide the toolbar, other songs, and the "+ New song" button.
  • Mobile UX is a standing requirement on every change, not a separate pass: any UI addition or alteration must also be adapted and verified at phone width (≤760px). New header controls need ≥44px touch targets; new modals must pick up the compact mobile styling (94vw sheet, tightened type, enlarged action buttons); drawer interactions must hand the full screen to the editor (close the drawer when a section, search result, or "+ Add section" is chosen, keep it open while naming a new song). Verify with the mobile Playwright suite (setbook-qa/mobile-drawer-test.js) plus a 390px visual pass.
  • When adding, changing, or removing a feature, update this documentation to describe it and refresh the "Last updated" date above.

12. QA regression checklist

Run this pass after any code change — especially refactors — before calling the work done. It is written so a human or an automated browser script can repeat it.

A. Static checks (fast, no browser needed):

  • Extract the inline <script> blocks and run node --check on them — JavaScript syntax must pass.
  • Verify balanced div / section / ul / button tags.
  • After a refactor, grep for dangling references to removed identifiers and confirm every modal open/close button has exactly one listener path.

B. Browser regression pass (serve the file over local HTTP, e.g. python3 -m http.server in the file's folder, then open it in a real browser with the console visible):

  • Load: no console errors; the welcome modal appears; the jsPDF library loads from CDN.
  • Welcome modal: dismisses cleanly via its start button.
  • Create content: add a song (title + artist), set its section type via the picker, add rows, type chords and lyrics. The live preview must reflect every edit.
  • Focus mode: click the ◎ button on a song header and confirm the search box, sort/filter controls, "+ New song", and other songs are hidden while the focused song's sections stay listed and selectable, and confirm the editor opens the focused song's top section (not whatever section was open in the previous song); click "← All songs" and confirm everything returns; reload and confirm the focus choice is restored.
  • Section naming: pick each section type and confirm the sidebar, preview, and a generated PDF show the derived name; add a second Chorus and confirm both become "Chorus 1" / "Chorus 2", then delete one and confirm the other reverts to "Chorus"; set a Custom name and a tag like (guitar solo); toggle Number single sections in File → Configuration… and confirm a lone Chorus becomes "Chorus 1" (and that a legacy custom "Verse 1" does not become "Verse 1 1"); open a legacy JSON whose sections only have name and confirm titles (including trailing parentheticals) survive unchanged.
  • Row actions: copy appends a duplicate with the same chords and lyrics at the bottom of the section; move up/down reorders; Clear chords clears only chords; Clear lyrics clears only lyrics; delete removes the row. No console errors.
  • PDF modal: the song checklist lists the song; Select all checks everything, Select none clears, Ready only selects just Ready songs (mark one song Ready first to verify). Generate a Performance PDF in light mode and in dark mode, and a Print-Friendly PDF — each must complete and produce a download with no errors.
  • Modals: Help, share/device-transfer help, copy-songs, Configuration, and the PDF dialog each open from their buttons and close both via their close buttons and via clicking the overlay background.
  • Configuration: open File → Configuration…; switch Appearance to Light and confirm the theme applies, then reload and confirm the choice persists; set Watch video links to Same tab and confirm the Watch button's tooltip changes, then set it back to New tab.
  • Sidebar: search filters the song list; title and artist sorting reorder correctly; Cover/Original and Ready/Not ready filters apply. Hiding the open song with a filter closes the editor to the empty starting view, and restoring the filter leaves the empty view (nothing auto-reopens).
  • Save: Save as produces a file download with no errors.
  • Narrow layout (mobile UX): at phone width (≤760px) the sidebar is a drawer opened by the 44px hamburger button and closes when a section, search result, or "+ Add section" is chosen (it stays open while naming a new song); header icon buttons and modal action buttons meet the 44px touch target; the welcome and PDF modals use the compact mobile styling with no horizontal overflow; no console errors.

C. Record the result. Note what was checked, the date, and any failures or limitations (e.g. a CDN dependency being unreachable in the test environment). Automated Playwright scripts covering the browser pass live alongside this checklist: setbook-qa/regression-test.js (56 checks) and setbook-qa/section-names-test.js (32 checks). A refactor that changes no user-visible behavior does not require a documentation update beyond this checklist's own "Last updated" date.
